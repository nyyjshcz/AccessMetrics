## 术语卡

| 术语 | 直白解释 |
| --- | --- |
| axe-core | 在浏览器页面上执行自动无障碍规则检查的引擎。 |
| WCAG A、AA | WCAG 的成功准则等级；本项目用它们做规则映射和计分资格判断。 |
| node | 规则实际检查到的一个页面元素。 |
| rule result | 一条规则在一个页面上的结果行，含结果类型和节点数量。 |
| opportunity | 一个可纳入评分的节点机会。 |
| impact | axe 给出的严重度，如 minor、moderate、serious、critical。 |
| scoring_eligible | 规则已映射到 WCAG A 或 AA，目录标为可计分，且节点结果为 pass 或 violation。 |
| pooled score | 把所有页面的计分机会合并到一个池中计算的分数，不是页面分数的平均。 |
| overlay | 叠加在原始结果上的人工或 AI 复核结论，不改写原始 axe 结果。 |

## 1. 先用一句话说清项目

AccessCheck Lishui 是一个本地运行的网页无障碍检查工具：

1. 用户输入一个网站首页和本次最多扫描页数；
2. 程序在同一站点内发现可访问的 HTML 页面；
3. 用 Playwright 打开页面，并用 axe-core 检查网页无障碍问题；
4. 将每条规则的节点数量、可复查的节点证据、页面状态和评分结果保存下来；
5. 对 axe 无法自动下结论的 incomplete 项，可由人工或 AI 给出辅助结论；
6. 生成可读、可复查、可发布的报告。

它的核心不是“给网站发一个神秘分数”，而是把可解释的自动检查结果转成一个严重程度加权、可复算的描述性评分，并保留证据与边界。

## 2. 你要理解的范围，以及不要混淆的范围

仓库中有两层东西，必须严格区分。

| 层次 | 当前是否是主程序运行逻辑 | 你需要掌握什么 |
| --- | --- | --- |
| 本地扫描与报告工具 | 是 | 数据如何产生、当前分数如何计算、AI/人工如何改变有效分数、报告如何解释 |
| analysis 目录中的离线研究分析 | 是可复现的辅助分析，但不是日常网页操作页 | 汇总统计、敏感性分析、人工复核一致性、导出完整性校验 |
| research、study 中的研究材料 | 不是当前本地工具的运行事实 | 可以用来了解项目演进；不能把研究流程、旧公式或样本设计说成现在的网页功能 |

当前项目不应被表述为“正式 WCAG 认证系统”，也不应把一次本地扫描说成随机抽样调查。它是一个以 axe-core 自动检测结果为基础、允许人工和 AI 辅助处理不确定项的审计工具。

## 3. 从用户操作到数学结果的数据流

    输入 URL 和本次页数上限
        ↓
    URL 校验与同源爬取
        ↓
    页面级 axe 扫描
        ↓
    rule_results（规则结果行，保存 node_count）
    result_nodes（violation / incomplete 的逐节点证据）
        ↓
    原始评分 raw score
        ↓
    人工 / AI 对 incomplete 的有效结论
        ↓
    有效评分 effective score
        ↓
    页面、站点、原则维度和报告展示

本地启动命令是 pnpm dev。它同时启动网页、扫描 Worker 与 AI Worker。常用页面为：

- 首页：/，查看活动任务和已发布报告；
- 新建扫描：/scans/new；
- 某一次扫描：/scans/[runId]；
- AI provider 设置：/settings/ai。

数学负责人不需要负责浏览器自动化实现，但必须知道结果不是凭空出现的：每个最终计分机会都来自一次具体页面上的规则结果。代码和测试不是必读材料，只在核对口径或复算结果时查阅。

## 4. 本次扫描的“样本”到底是什么

### 4.1 页数上限不是保证扫描到多少页

表单里的最大页数是本次爬取的上限，不是“必须成功得到这么多页面”的承诺，也不是抽样大小。当前输入允许 1 到 15 页，页面表单默认 10 页；服务端配置的默认上限是 15 页。爬虫可能提前结束，因为：

- 同源范围内没有更多候选链接；
- 超过了抓取深度或总时长；
- robots 规则不允许；
- 链接重定向后与已有页面重复；
- 地址不是可扫描 HTML、不是允许协议，或被资源类型过滤；
- 某页面抓取、渲染或扫描失败。

所以“发现 9 页、成功 6 页、失败 1 页”时，另外两页通常仍在队列、被跳过、被去重、或因爬取规则未进入最终页面记录；它不等于“少抽了两份随机样本”。页面记录的发现、成功、失败和未完成状态是页面层状态，不要求相加后等于页数上限。

### 4.2 不能作出的统计推断

扫描到的页面是由站内链接结构、爬取规则和技术可访问性决定的便利集合，而不是从全站页面随机抽取的概率样本。因此不能从当前结果直接推出：

- 全网站真实合规率；
- 某城市、某类网站或所有用户的总体比例；
- 置信区间、显著性检验或因果结论；
- axe 的总体准确率、误报率或漏报率。

如果以后要提出上述结论，需要另行定义总体、抽样框、随机或分层抽样方案、纳排标准和人工金标准；现有程序没有自动完成这些工作。

## 5. 最重要的计数单位：规则、节点、机会

这三个概念最容易被误读。

| 名称 | 数据位置 | 意义 | 可不可以直接当作别的单位 |
| --- | --- | --- | --- |
| 页面 page | pages | 一个被发现或尝试扫描的 URL | 不等于一个独立随机观测 |
| 规则结果 rule result | rule_results | 某个页面中某条 axe 规则的一行结果 | 不等于问题节点数 |
| 节点数量 | rule_results.node_count | 页面中落入该规则结果的元素数量，也是当前评分的基本粒度 | 不是逐节点证据条数 |
| 节点证据 | result_nodes | violation / incomplete 节点的具体元素、HTML 片段和定位信息 | 不是所有结果类别的节点总数 |
| 计分机会 opportunity | 由合格节点转换 | 一个可判为通过或失败的节点 | 是公式的分母单位 |

例如，一条规则在一个页面触发 30 个节点，数据中是一个 rule_results 行，但对整体分数有 30 个节点机会，而不是 1 个。

### 5.1 为什么不能用 result_nodes 的行数统计所有节点

为节省存储，程序只持久化 violation 和 incomplete 的逐节点证据。pass 与 inapplicable 不会写出一条条 result_nodes。它们的真实数量在 rule_results.node_count。

所以：

- 所有结果类别的总节点数，要汇总 rule_results.node_count；
- violation / incomplete 的具体元素、HTML 片段和定位信息，才从 result_nodes 读取；
- 把 result_nodes 的行数直接当作“全部通过/失败节点总数”会系统性低估 pass 与 inapplicable。

报告代码和运行时计分都遵循这个规则。数学负责人在核数时必须先问：这里报的是规则行数，还是节点数？

## 6. 哪些结果真正进入当前分数

axe 的结果类型包括 pass、violation、incomplete、inapplicable。当前评分的处理方式如下。

| 原始类型或状态 | 原始分数是否计入 | 原始含义 |
| --- | --- | --- |
| pass | 计入，权重 0 | 自动检查通过 |
| violation | 计入，按严重程度扣分 | 自动检查判为问题 |
| incomplete | 不计入 | 自动规则无法下结论，等待人工或 AI 辅助判断 |
| inapplicable | 不计入 | 规则不适用于该节点 |

另外，不是所有 violation 都有资格进入分数。规则必须由冻结的 WCAG catalog 映射为 WCAG A 或 AA，且标记为 scoring_eligible。最佳实践、仅 AAA、未知或未映射的规则仍会显示在证据与报告中，但不会进入分数分子或分母。

这意味着“报告里看到的问题总数”和“导致分数下降的问题数”不一定相同。两者回答的是不同问题：

- 报告问题总数回答：扫描看到了什么；
- 评分问题数回答：当前定义下哪些 WCAG A/AA 自动结果进入了分数。

## 7. 当前主评分公式

### 7.1 定义

令 E 为本次运行中所有符合计分资格、且已能判断为通过或失败的节点机会集合。令 N = |E|。

对每个机会 i，定义严重程度权重 w_i：

| 结果 | w_i |
| --- | --- |
| pass | 0 |
| minor | 1 |
| moderate | 2 |
| serious | 3 |
| critical | 4 |

当前主分数为：

    S = 100 × (4N − Σw_i) / (4N)

等价地：

    S = 100 × (1 − Σw_i / (4N))

分数越高，表示在这个被计入的节点集合中，按当前严重程度权重累计的自动问题越少。

代码内部为了使用整数精确计算，把上述权重统一乘以 10：

    minor = 10，moderate = 20，serious = 30，critical = 40，最大权重 = 40

这个缩放不会改变最终数学结果。实现以整数分子、分母保存，最后才做一次显示舍入，避免浮点误差和逐页舍入误差。

### 7.2 一个手算例子

某次扫描中，有 8 个可计分 pass、1 个 serious violation、1 个 moderate violation。

    N = 10
    Σw_i = 3 + 2 = 5
    S = 100 × (4×10 − 5) / (4×10)
      = 100 × 35 / 40
      = 87.5

注意：这不是“80% 节点通过，所以 80 分”。它是每个失败节点按严重程度扣不同额度的加权结果。

### 7.3 无严重程度时如何处理

某个 violation 可能没有直接的节点 impact。当前代码按以下顺序确定其计分严重程度：

1. 节点本身的 impact；
2. 所属 rule result 的 impact；
3. 仍不存在时，默认 minor。

报告会保留该影响来源。数学上这避免了一个已判定的 violation 因缺少严重程度字段而从分母中消失；解释上应诚实说明这是项目的保守默认，不是 axe 给出的额外事实。

### 7.4 无可计分数据时

如果 N = 0，真实运行的 overall score 应显示为 N/A（无可计算数据），而不是 0 分或 100 分。因为没有合格的、已判定的计分机会，任何百分制值都没有定义。

## 8. 站点分数不是“页面分数的平均”

站点总分直接把全运行的合格机会合并后计算：

    S_site = 100 × (4ΣN_page − ΣW_page) / (4ΣN_page)

它不是：

    (第 1 页显示分 + 第 2 页显示分 + …) / 页数

原因有两个：

1. 不同页面的节点数量可能相差很大，简单平均会让只有一个节点的页面与几百个节点的页面权重相同；
2. 页面显示分已经四舍五入到一位小数，再平均会引入额外误差。

如果要说明项目的聚合方式，应说“按所有符合资格的节点机会池化计算”，不能说“每页平均分”。

## 9. 四项原则分数：是什么，不是什么

项目按 WCAG 四项原则显示可感知、可操作、易理解、兼容性四个子分数。每个机会会带有一个或多个原则标签。

- 总分中，一个节点只计一次；
- 某节点若映射到多个原则，在每个相关原则的诊断子分数中都可以出现；
- 所以四项原则的机会数可以相加后大于 overall 的机会数；
- 四项原则分数用于定位哪类问题更突出，不能把四个显示分数再取平均来“复算总分”。

### 9.1 一个必须知道的代码与文档差异

scoring/scoring-config.v1.json 和 scoring/model-spec.md 中出现过 40/30/20/10 的原则权重叙述，但当前运行的主评分函数没有把这些原则权重用于 overall score。现行 overall 仅由节点严重程度权重和节点机会数决定。

因此，当前对外解释必须以运行代码为准：

- 正确：总分是所有合格节点的严重程度加权池化分数；
- 不正确：总分按四项原则 40/30/20/10 再加权合成。

这是需要在后续维护中持续留意的“文档与实现差异”，不是可以凭旧文档自行补上的公式。

## 10. raw score 与 effective score

项目刻意保留两个分数。

| 分数 | 使用什么数据 | 是否改动原始 axe 结果 |
| --- | --- | --- |
| raw score | 原始 pass 与 violation；incomplete 不计分 | 否 |
| effective score | 原始结果加上对 incomplete 的人工/AI 有效结论 | 否，结论以 overlay 方式叠加 |

对一个原始 incomplete 节点，effective score 的映射为：

| 有效结论 | 转换后的计分机会 |
| --- | --- |
| problem | 视为 violation，按原始有效 impact、规则 impact 或 minor 默认值计分 |
| not_problem | 视为 pass，权重 0 |
| uncertain | 仍不进入分数 |
| 尚无结论 | 仍不进入分数 |

因此 AI 或人工处理 incomplete 后：

- raw score 不会改变；
- effective score 可能改变；
- 原始 incomplete 总数不会被改写；
- 报告应同时表达“原始机器结果”和“当前有效结论”，不能假装 AI 把原始 axe 事实覆盖掉了。

### 10.1 人工优先级

同一节点若同时存在多种结论，当前优先级为：

    本地人工当前结论 > 最新完成 AI 批次的结论 > 原始 incomplete（未解决）

人工可覆盖 AI，是因为 AI 只是辅助判断。不能将 AI 结论说成最终人工审计结论。

### 10.2 coverage 指标是什么

对于原始 incomplete 节点总数 T：

    processed coverage = (problem + not_problem + uncertain) / T × 100%
    resolution coverage = (problem + not_problem) / T × 100%

如果 T = 0，代码显示 100%，表示“没有需要处理的项”，不是“模型识别准确率 100%”。

这两个指标只描述不确定项的处理进度，不能解释为无障碍质量、AI 准确率或统计置信度。

## 11. 报告中的数字如何读

报告至少有四类不同数字：

| 报告数字 | 正确含义 | 常见错误读法 |
| --- | --- | --- |
| 页面数 | 已发现或完成扫描的页面记录 | 代表全站所有页面 |
| 规则数 | 不同规则结果行的数量 | 等于问题元素数量 |
| 节点数 | rule_results.node_count 的加总 | 任何结果类型都能从详细节点表直接数出 |
| raw / effective 分数 | 两种明确数据口径下的加权分数 | “网站已经官方认证合规” |

对于 violation 与 incomplete，报告可列出 selector、HTML 片段、帮助链接等证据；pass 与 inapplicable 的完整逐节点 HTML 并不持久化。这里的“没有细节”是存储策略，不代表节点数为 0。

若页面有 frame coverage limited 或 coverage_limited，这仅表示跨域 frame 等范围没有完整覆盖。它不能被重新解释为 pass，也不应被偷偷纳入“无问题页面”。

## 12. 离线研究分析中的统计部分

analysis/analyze.py 是离线分析脚本，面向验证过的导出数据。它与网页上的一次扫描不同，重点是多运行或多站点的描述性汇总。

### 12.1 首先是数据完整性校验

脚本在统计前验证：

1. manifest.json；
2. manifest.sha256；
3. 每个导出负载文件的 SHA-256。

校验失败时不应继续把输出当作可信统计结果。数学负责人应把这看成可复现性的一部分：先证明输入没有被悄悄改动，再讨论均值或相关性。

### 12.2 总体分数与站点分布

离线输出中的 overall score 也是把所有合格机会池化计算。高节点数站点自然在 pooled overall 中拥有更多权重。

而分布统计中的 site score 是每个站点的一位小数显示分数，随后计算：

- 样本量 n；
- 均值 mean；
- 中位数 median；
- 第一、第三四分位数 Q1、Q3；
- 最小值、最大值。

四分位数采用线性插值，位置为 (n − 1)p；其中 Q1 的 p = 0.25，Q3 的 p = 0.75。它表示排序后数据中间位置的范围，不能当作总体比例或准确率。因为它使用的是显示到一位小数后的站点分数，复算时应使用同一口径；不要把精确 pooled overall 与显示分数分布混成一个数。

这些都是描述性统计：均值和中位数描述分布的中心，Q1 和 Q3 描述中间一半数据的大致范围，最小值和最大值描述观察到的边界。它们不能推出外部总体比例、准确率或统计显著性；若导出集合不是随机样本，也不应把均值解释为外部总体均值。

### 12.3 类别比较、严重程度和常见规则

离线脚本还会计算：

- categoryComparison：按 data/sites.csv 给出的类别，对一位小数站点分数做描述性比较；
- severitySummary：对 violation 节点按 effective impact 汇总；
- commonRules：对 violation 与 incomplete 节点按规则 ID 汇总；
- sampleSummary.populationSize：当前定义为 violation 节点加 incomplete 节点数量。

它们适合回答“在这批导出里，哪些规则和严重程度更常见”，不适合回答“某规则在全市所有网站中的真实发生率是多少”。

## 13. 敏感性分析：测试的是排名稳健性，不是显著性检验

当前可执行的 TypeScript 和 Python 实现固定计算三个严重程度权重情景：

| 情景 | critical | serious | moderate | minor |
| --- | ---: | ---: | ---: | ---: |
| A，主模型 | 4 | 3 | 2 | 1 |
| B | 5 | 3 | 2 | 1 |
| C | 4 | 2.5 | 1.5 | 1 |

同一批站点在每个情景下都重新按精确分数计算并排序。排序规则是：

1. 分数从高到低；
2. 分数完全相同，用站点 ID 的字母顺序稳定排序；
3. 输出竞争排名，例如 1、1、3。

脚本还计算情景两两之间的 Spearman 秩相关。它衡量两个情景下相对排名是否相近，不衡量分数本身的差值。对 ties，它先用平均秩处理，再计算秩向量的 Pearson 相关；可比较站点少于 2 或排名没有变化时，结果为 null。它不能推出总体比例、准确率或统计显著性。

应这样解释：

- 较高的 Spearman 值：在这些人为设定的严重程度权重变化下，站点相对排名较稳定；
- 较低的 Spearman 值：排名对权重选择更敏感，结论应更谨慎；
- 它不证明模型正确，不是因果关系，也不是统计显著性；
- 只比较共同存在的站点，不可把缺失站点当作 0 分。

### 13.1 又一个必须注意的历史配置差异

scoring/sensitivity-configs.json 包含 equal-principle、page-macro-average、density 等更丰富的方案名称，但当前实际可执行的 src/lib/sensitivity.ts 和 analysis/analyze.py 并没有消费并运行这些配置。现在真正会产出的只有上述 A/B/C 三种严重程度情景。

所以不能仅因 JSON 文件里有一个方案名，就声称项目已经做了该方案的敏感性实验。

## 14. 人工复核一致性：只适用于历史研究导出

历史离线研究流程可能有两位复核者的 manual-reviews.json。当前脚本只在一条节点同时有 computer 与 math 两个角色的完整复核时形成配对。Cohen’s κ 衡量两位复核者在扣除偶然一致后的分类一致程度；它不能推出总体比例、axe 准确率或统计显著性。

设完整配对数为 n_pairs，分类标签为 l。

观察一致率：

    A = n_agree / n_pairs

Cohen’s kappa 的实现为：

    P_o = A
    P_e = Σ_l [n_computer(l) × n_math(l)] / n_pairs²
    κ = (P_o − P_e) / (1 − P_e)

若没有完整配对，或 P_e = 1，脚本返回 null，而不是伪造一个数。

其正确解释范围是：

- 这批被复核节点上，两位复核者对标签的一致程度；
- 不是 axe 的准确率；
- 不是全网站、全城市或全部节点的误报率；
- 不是机器学习模型的泛化性能。

旧研究数据中的标签可能叫 confirmed、not_an_issue、uncertain；当前本地页面使用 problem、not_problem、uncertain。语义相近但数据流程不同，讲解时不要把历史双复核机制误说成当前每一次本地扫描都会自动执行。

## 15. AI 与速率控制不是统计模型

当前 AI Worker 只处理 incomplete。provider 可以配置最大同时在途请求数，且某些 OpenRouter 免费模型可选择 20 请求/分钟的节流策略。它们是任务吞吐、服务端限流和成本控制设置，不属于评分公式，也不能改善原始 axe 的统计代表性。

尤其要区分：

- AI 给出 problem/not_problem/uncertain，是对某一不确定节点的辅助判断；
- AI batch 的完成数、失败数、排队数，是运行监控数字；
- AI 处理覆盖率不是准确率；
- 服务端 429、网络错误或返回格式错误，是运维事件，不是数学结果。

## 16. 可以怎样严谨地描述项目结论

下面是可用和不可用说法的对照。

| 可以说 | 不应说 |
| --- | --- |
| 在本次扫描覆盖到的页面和符合资格的节点中，按当前严重程度权重计算的分数为 X | 该网站官方通过了 WCAG 认证 |
| 分数由 eligible pass 与 violation 节点的 pooled 结果计算 | X% 的网站页面绝对无障碍 |
| incomplete 未直接计入 raw score，人工/AI 结论可改变 effective score | AI 已证明这些问题真实存在或不存在 |
| 四项原则分数用于诊断不同类型的风险 | 总分是四项原则显示分数的简单或固定权重平均 |
| 离线导出的均值、中位数和排名反映导出集合 | 这些统计可代表未抽样的所有网站 |
| 敏感性分析检验相对排名对严重程度权重的稳健性 | 敏感性分析证明评分模型客观正确 |

## 17. 数学负责人应能亲自复算的最小练习

完成下面几项，就说明你不只是“看过公式”。

1. 对 8 个 pass、1 个 serious、1 个 moderate 手算 87.5；
2. 构造两个页面：一页 1 个 critical，另一页 99 个 pass。说明为何站点 pooled score 不等于两个页面分数的简单平均；
3. 解释一个 multi-principle 节点为什么会出现在两个原则子分数里、却只计一次 overall；
4. 解释 raw score 与 effective score 的差别，并说明 manual 覆盖 AI 的原因；
5. 看到 pass 节点数和 result_nodes 行数不一致时，说明应去哪里核数；
6. 看到 N/A 时，说明这是没有可计分机会，而不是 0 分；
7. 看到某批导出的 Spearman 值时，说明它能够、不能够支持什么结论；
8. 看到人工一致率或 κ 时，准确说出它的样本范围。

## 18. 复算和审计入口

优先通过 API、报告 JSON 或测试核对，不要手工修改 SQLite 数据库。

常用命令：

    pnpm dev
    pnpm exec vitest run tests/scoring/score.test.ts tests/scoring/ai-overlay.test.ts
    pnpm score:recalculate <runId>
    pnpm test:all

若需要只读核对数据库中的节点数，核心思路是按 rule_results.node_count 汇总，而不是只数 result_nodes：

    SELECT result_type, SUM(node_count) AS nodes
    FROM rule_results
    WHERE run_id = ?
    GROUP BY result_type;

    SELECT impact, SUM(node_count) AS nodes
    FROM rule_results
    WHERE run_id = ? AND result_type = 'violation'
    GROUP BY impact;

当前运行结果可通过 GET /api/runs/[runId] 读取 rawScore、score、页面状态、计数和 coverage。已发布报告的 JSON 还会把精确分数的分子、分母以字符串形式保留，便于不受 JavaScript 浮点数影响地审计。

## 20. 最后的检查清单

在任何展示、写作或回答前，先逐项确认：

- 我说的是节点数、规则数还是页面数？
- 我说的是 raw score 还是 effective score？
- 我是否把页数上限误说成随机抽样数量或全站覆盖？
- 我是否把 pooled score 误说成页面平均分？
- 我是否把四项原则子分数误说成总分的固定权重组成？
- 我是否把 incomplete、AI 处理覆盖率或人工一致率误说成准确率？
- 我是否清楚某个统计是当前本地工具产出的，还是旧研究导出流程的结果？
- 我是否清楚结论只覆盖本次扫描、当前规则映射、当前权重和当前数据范围？

如果以上每一项都能结合代码和一个具体运行实例解释清楚，数学部分就已经真正掌握，而不是只会复述几个名词。
