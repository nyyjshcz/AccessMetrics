# AI Worker 生命周期、复核范围与费用监控设计

## 目标

让每一项 AI 复核都能追溯到一个仍然存在的扫描任务；让暂停、继续、换模型、重跑、删除有不同且可预测的含义；彻底避免扫描任务被删除后仍有 AI 队列或重试继续运行。管理员应能看到当前 Worker 在处理什么，以及实际发出的 API 请求和可获得的费用信息。

页面刷新和重新打开只读取持久化状态，绝不创建批次、恢复任务或发起 AI 请求。

## 对象与统计口径

```text
扫描任务（所有者）
└── AI 复核批次（一次明确发起的处理周期，绑定不可变模型配置快照）
    ├── 复核项目（本批次中每个扫描项目的最终处理状态）
    └── API 调用记录（一次实际请求；自动重试也各自计为一次调用）
```

- 扫描任务是 AI 批次的唯一业务父级；不得创建脱离扫描任务的可执行 AI 工作。
- 每个批次固定一份模型配置快照。API 密钥不写入快照、任务历史或日志。
- 批次项目数、批次状态数、实际 API 调用数是不同指标，必须分开展示。
- 重试只增加 API 调用记录，不额外增加复核项目数。跨批次的历史总数不得冒充当前批次或当前扫描的进度。
- “全部重跑”是有意新建的批次，因此同一个扫描项目可以出现在多个历史批次中；当前进度按所选批次显示，扫描级概览按项目去重。费用与调用统计按真实请求记录汇总。
- 运行概览只统计当前可执行批次；历史项目数必须明确标注为历史累计，不能把所有 `ai_review_items` 行直接相加后称为当前项目状态。

## 用户确认的复核范围

按钮语义必须明确区分：

1. **继续任务 / 继续未完成项**：只处理当前扫描复核范围内尚未成功的项目，包括排队中、暂停中断后待处理以及失败项目；已成功项目不再次调用模型。
2. **按当前模型全部重跑**：对本扫描的完整 AI 复核范围重新处理，明确包含已经成功的项目。该操作创建新批次并产生新的 API 费用；旧批次及其结果留作历史，不与新批次进度相加。

完整 AI 复核范围以本次扫描的复核候选项目为准；已有人工最终结论的项目不再发给 AI。即使扫描、模型和提示词都未变化，管理员再次确认“全部重跑”也必须创建独立的新批次。重复提交同一次按钮请求只创建一次；另一次明确的重跑操作可再创建新批次。

若原批次模型配置没有变化且处于暂停状态，“继续任务”恢复同一批次，只处理未成功项目；失败项目进入一次新的、有限次的显式继续周期，旧 API 调用和失败原因仍保留。若模型配置已变化或删除，旧批次不可恢复；“继续未完成和失败项”以当前选定配置创建一个新批次，范围仅含未成功项目。“全部重跑”则以当前配置创建新批次，范围含全部项目。

AI 复核结果不得覆盖规则检查结果或人工结论。新批次结果与旧批次分开保存；用户可识别每项结果来自哪个模型和批次。人工结论始终优先展示。

## 生命周期规则

### 开始与运行

- 只有管理员明确点击开始、继续或重跑，才会创建或激活批次。
- Worker 领取每个项目及发送每次请求前，都必须校验：扫描仍存在且允许复核、批次处于 `queued` 或 `running`、没有取消/暂停信号、批次配置快照仍有效，并且当前批次仍是该扫描唯一可领取的批次。
- 批次有持久化状态和版本/栅栏标识。暂停、取消、配置变更或删除会使旧 Worker 的租约失效；过期 Worker 返回的结果不能复活旧批次或覆盖新批次。
- 每次领取项目必须有唯一的尝试/租约标识；完成、失败和取消写入同时校验该标识与批次版本。Worker 名称或槽位不能充当唯一标识。过期租约上的迟到响应只更新其调用审计，不能更新当前项目。
- 自动重试仅允许发生在有效的活动批次中，且每项目、每个显式处理周期最多 3 次 API 调用（首次加最多两次自动重试）。管理员显式继续会开启新的有界尝试周期，但不清除旧 API 调用记录或错误历史。退避等待期间也必须重新验证批次和扫描状态；暂停或取消后不得执行待触发的重试。
- Worker 重启只能继续仍处于活动批次中的原有待处理队列，不得自行把 `failed`、`paused` 或 `cancelled` 批次重新激活，不得清零失败项的尝试数或自动开启新周期。对可能已经发送给服务商、但结果不确定的中断请求，记录“结果未知/已中断”并等待管理员明确继续，避免隐式重复付费。

### 暂停与继续

- 暂停是可恢复的停止：事务性地阻止领取新项目和重试，并向在途请求发出中止信号。待处理项目保留，失败项目及其原因保留，批次显示 `paused`。
- 在途调用显示“取消中”直至响应或中止确认。若服务商已经收到请求，客户端不能保证撤销计费或退款；最终调用结果仍写入 API 调用记录。
- “继续任务”只恢复配置快照仍有效的暂停批次；处理所有未成功项目，包括暂停前失败的项目，不重跑成功项。继续动作必须由管理员明确触发。
- 继续后失败项目进入新的有限尝试周期；每项目每周期仍最多 3 次 API 调用。所有周期的尝试记录和脱敏失败原因均可追溯，绝不因为重置本周期次数而删除历史。
- 服务端的通用重试入口不得绕过暂停；处于暂停或取消中的批次只能通过受校验的显式“继续”操作改变状态。页面显示“暂停中”直至在途调用已确认结束或被中止，不能提前把仍有活动请求的批次当作完全静止。

### 模型配置变更、停用或删除

- 保存对批次所绑定模型配置的修改、停用或删除，会立即使该配置快照下所有非终态批次失效：停止领取、停止退避重试并请求中止在途调用。
- 不删除未完成项目、失败项目、错误原因或 API 调用记录；批次标记为 `cancelled/superseded`，说明停止原因和时间。已完成结果保留。
- 模型切换取消旧批次时同样保留其所有项目明细。人工结论使项目不再需要 AI 时，使用带原因的非可执行标记，不物理删除旧项目或失败历史；只有删除父扫描任务才删除关联项目。
- 配置变更本身不启动新模型、不自动重跑。用户必须明确选择新配置并点击对应范围按钮。
- 一次扫描最多只有一个可领取批次。旧批次先持久化停止，新批次即使已创建，也须等旧批次在本机发出的请求全部结束/中止或达到硬超时并完成栅栏收尾后才能发出新请求。迟到结果仅归入旧调用记录，不改变新批次进度。

### 删除扫描任务

- 删除扫描任务时，先提交持久化的删除/取消栅栏，使跨容器 Worker 能观察到它并阻止领取和发送；再请求中止在途 AI 请求，最后清理该扫描对应的所有 AI 批次和复核项目。清理步骤须可重试；已删除任务下不得残留可恢复、可重试的 AI 任务。
- 保留去标识化的 API 费用审计：移除扫描、批次、项目及目标站点关联，只保留真实调用的时间、模型标识、状态、脱敏错误和服务商实际返回的 token/费用。若服务商不返回费用则显示“未知”，不按标价估算。
- 删除任务不删除其他扫描、报告、模型配置或其他任务的审计记录。

### 终态

- `completed`：该批次范围内所有项目已成功；无活动领取。
- `failed`：未成功项目已达到该周期尝试上限或遇到不可恢复错误；不自动重试。
- `cancelled/superseded`：由配置变化、管理员停止或父扫描删除导致。配置变化保留批次明细；父扫描删除按上述规则删除任务明细并去标识审计。
- `paused` 与 `cancelled` 不计入活动队列；仅 `queued/running` 可领取。

## 管理员页面

完善现有 AI Worker 监控页，并从 AI 设置和活动扫描任务提供入口，不再新增第二套重复监控页。页面状态均从服务端持久化数据读取：

- **当前运行**：扫描任务、批次、模型、正在处理的项目、安全的项目标识、开始时间/运行时长、尝试序号；当前没有请求时明确显示“当前无 AI 请求”。
- **队列与批次**：分开统计 queued、running、paused、completed、failed、cancelled/superseded；列表展示停止原因、项目数和最近更新时间。全局历史批次统计必须明确标注“历史累计”，不得和当前扫描/批次进度混在一起。
- **调用与用量**：近期真实 API 请求的时间、批次/模型、成功或脱敏错误、耗时、尝试序号，以及服务商实际返回的 token 和费用。服务商不提供时显示“未知”。
- **扫描复核进度**：每次只展示所选/最新批次的项目数和进度；全扫描汇总按扫描项目去重，不能把多个批次相加制造出大于扫描范围的当前待处理数。
- 批次必须保存停止原因及时间；删除扫描后保留下来的去标识调用审计明确标为“已删除任务的历史调用”，不能误显示为无来源的活动请求。
- 页面轮询只读；刷新或重新登录不改变任务状态。
- 不显示 API 密钥、完整目标 URL、请求头、提示词、被检查网页内容或模型完整响应。

## 界面操作

- 无批次：`开始 AI 复核`。
- 活动批次：显示当前实际使用的模型及进度，提供 `暂停`；若用户想更换配置，明确先停止当前批次，并告知在途请求可能仍产生一次费用。
- 暂停且原配置未变：提供 `继续任务`，只续做未成功项。
- 配置已变或批次已取消：显示停止原因与历史失败数；提供 `按当前模型继续未完成和失败项` 与 `按当前模型全部重跑 N 项` 两个独立操作。后者确认框须明确包含已成功项目及预计处理项目数。
- 失败批次：错误仍可查看；“继续未完成和失败项”创建新周期，不抹去旧失败历史。
- 删除扫描任务的确认文案需说明关联 AI 队列及批次会一并删除，且在途 API 请求可能尚未及时终止。

## 当前问题的修正目标

- 配置变更取消批次时，不能再删除 queued/failed/running 复核项目来掩盖失败或缩小历史批次。
- 不再把批次数量、复核项目数、调用次数或多个批次的累计结果混成一个数字。
- 旧配置批次取消后，界面不能只显示“等待状态更新”或提供错误的继续按钮；必须显示终止原因和适用的新操作。
- 暂停、配置变更、删除与退避重试之间必须通过持久化状态及栅栏检查消除竞态。

## 实现边界

- 重点检查队列、Worker、持久化仓库、扫描删除与模型配置保存/删除 API、管理员监控 UI/API。
- 允许新增数据库迁移、API 调用审计字段与管理员只读监控 API；不改扫描评分和规则结果，不改模型 API key 的现有配置方式。
- 审计字段只记录必要、脱敏的元信息；绝不保存密钥、提示词、目标页面正文或完整模型响应。
- 中英文界面文案保持同一操作语义。

## 验收标准

1. 暂停后不会领取新项目、触发任何退避重试或再次调用模型；在途请求被请求中止并能显示其最终调用状态。
2. 同配置显式继续时，只处理未完成和失败项；成功项不被重跑。
3. 配置编辑、停用或删除后旧快照批次立即停止；失败及待处理历史可见，且不自动新建批次。
4. 新配置下“继续未完成和失败项”只创建这些项目；“全部重跑”覆盖完整复核范围且包含已成功项目。两者均有独立批次、独立进度和调用记录。
5. 同一扫描不会有两个可领取批次；旧 Worker 的迟到响应不能覆盖新批次状态或重新排队。
6. 删除扫描后，其任务型 AI 批次和项目记录均不存在且不可恢复；去标识调用审计保留，不含任务和目标站点关联。
7. 监控页准确区分批次、复核项目和 API 调用；跨批次历史不会伪装成当前进度，刷新不会触发任务。
8. 每项目每显式处理周期最多 3 次 API 调用；单元/集成测试覆盖暂停与重试竞态、配置修改/删除、全量重跑与未完成续做、父任务删除、用量脱敏及监控权限。
9. 验证使用本地假模型，不调用真实 AI、不新建真实扫描；本地 Docker 验证后再按既定局域网镜像流程部署 NAS。
10. Worker 重启、过期租约和迟到响应不会自动打开失败批次、重置重试上限、重复调用或覆盖新结果；暂停状态不能由通用重试 API 绕过。
11. 同模型再次确认全量重跑生成新批次；换模型后的“继续”只包含旧批次未成功项目；监控的当前项目数不累计历史批次行。

## 明确不做

- 不接入服务商账单 API，不推测或声称能精确还原服务商未返回的历史费用。
- 不自动恢复取消批次，不在模型配置变更后自动迁移或重跑。
- 不改变扫描评分、规则判断、人工结论、报告结构或现有角色权限。
