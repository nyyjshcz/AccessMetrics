# AccessCheck Lishui：当前项目说明

> **谁需要读：所有人。是否必读：是。** 读完你会知道项目的目的、使用流程、报告怎么看，以及哪些结论不能从扫描结果推出。

## 这个项目要解决什么

AccessCheck 是一个可自托管的网页无障碍评估工具。它从一个公开网站首页开始，在同一站点内发现页面，以真实浏览器状态运行 axe-core 自动检查，保留规则、节点和页面证据，再以结构化报告呈现结果。

它的目标不是替代无障碍专家，也不是给网站贴上“合规”或“不合规”的标签。它要做的是让一次网页无障碍初筛具备三件事：

1. **可重复**：同一输入会经过明确的 URL 校验、页面发现、浏览器渲染和规则检查过程。
2. **可解释**：每个问题可以回到规则、页面、目标元素和清理后的 HTML 证据。
3. **可沟通**：报告先展示评分、覆盖范围和高优先级事项；复杂证据按需展开。

## 一个使用者会经历什么

管理员输入网站地址 → 扫描 Worker 发现同站页面并以 Playwright + axe 运行检查 → SQLite 保存页面、规则结果、节点证据和原始评分 → 人工或 AI 对 incomplete 项补充复核结论 → 管理员发布只读报告 → 持有访客密钥的人只能查看已发布报告。

详细的数据流见[架构说明](./architecture.md)，无需通读即可继续使用项目。

## 主要结果如何阅读

### 1. 页面覆盖先于分数

“最多扫描 15 页”是某次任务的上限，不保证一定会扫描到 15 页。当前输入范围是 1 到 15 页，页面表单默认 10 页；服务端配置的默认上限是 15 页。站点可能没有足够多的独立页面，重复或重定向页面会合并，页面也可能扫描失败。

页面层的扫描状态描述页面工作本身：已发现、成功、失败，或仍未完成。规则或节点层的 `incomplete` 是 axe 对某项结果“还不能可靠判断”的标记。两层状态可以同时存在：例如页面扫描成功，但其中某条规则仍有 `incomplete` 节点。

### 2. 自动问题与需进一步判断项目不同

首次出现的 `result` 类型有四种：`violation` 表示问题，`pass` 表示通过，`incomplete` 表示还需进一步判断，`inapplicable` 表示不适用。`pass` 进入原始分数；`inapplicable` 不计分；`incomplete` 不直接计分，但人工或 AI 复核结论可以影响有效分数。

`violation` 会进入自动问题列表。`incomplete` 不会被偷偷算作自动问题；人工或 AI 只能补充结论，不能覆盖原始 axe 记录。

### 3. 有两个并列分数

- **原始评分**：只根据原始自动扫描结果计算。
- **复核后评分**：在原始结果之上，纳入已完成的人工或 AI 对 incomplete 项的结论。

人工判断优先于 AI 判断；没有得到有效补充结论的项目仍显示为原始 incomplete。评分是用于筛查、比较和定位问题的量化信号，不是 WCAG 合规认证。

## 两类访问者

| 身份 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 管理员 | 新建扫描、查看任务、配置 AI、复核 incomplete、发布报告、删除未发布的终态任务 | 不能修改已发布扫描。 |
| 报告访客 | 阅读、下载已发布报告 | 不能扫描、改配置、处理 AI、删除数据或查看未发布结果。 |

浏览器登录使用管理员密钥或访客密钥。服务器另有 `SESSION_SECRET`：它用于签名会话 Cookie，也用于加密已保存的 AI Provider Key，不交给任何使用者。丢失或更换它会使现有会话失效，并使已保存的 Provider Key 无法解密。

## 对项目展示最重要的四个事实

1. 系统使用浏览器实际渲染页面，而不是只抓取 HTML 字符串。
2. 系统保留节点级证据，因此报告不只是一串分数或问题数量。
3. 完整性被明确呈现：失败页面、未覆盖 frame 和 incomplete 项不会被伪装成“通过”。这里的“未覆盖 frame”指页面中的嵌入框架未被检查。
4. 已发布报告是只读的，避免演示或评审时结果在后台继续变化。

## 不能夸大的地方

- 不能说“扫描覆盖了整个网站”，只能说覆盖了本次实际成功扫描的页面。
- 不能把 0 到 100 分解释为完整人工审计结论或官方 WCAG 合规率。
- 不能把 AI 判定说成专家审查；它是对 incomplete 项的辅助复核，并且人工结论优先。
- 不能把本地 SQLite 的小规模实现说成大型生产平台。
